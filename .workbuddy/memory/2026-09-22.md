## 启动失败：application.yml 被写入字面 `/n`（已修）
- 现象：Spring Boot 起不来，`ScannerException: while scanning a simple key ... line 84 daily-bar:/n    # 关掉... could not find expected ':'`。
- 根因：09-21 加 `market.daily-bar` 配置时用的是 `node -e "..."` 内联脚本，**字符串里的 `\n` 被 shell 转义链吞掉，写进文件的是字面 `/n` 两个字符**（正斜杠 + n，不是反斜杠 n）。
  结果 `daily-bar:` 与后面的注释挤在同一行，YAML 把它当成一个没有 `:` 结尾的 key，下一行 `enabled: true` 就成了意外 token。
- 修法：脚本改成 Write 落盘再执行，把 `  daily-bar:/n    # 关掉` 换回 `  daily-bar:\n    # 关掉`；已用 pyyaml 全量解析校验通过，`market.daily-bar` 五个键（enabled/lead-days/volatile-days/max-age-days/volatile-ttl-ms）齐全。
- 教训（长期）：**凡是往文件里写多行文本，一律用 Write 工具落 .js 脚本再跑，不要用 `node -e "..."` 内联带 `\n` 的字符串**——本机 Git Bash 的转义链会把 `\n` 变成 `/n`，且这种错误不会在编译期暴露，只在运行时炸。Java 文件那批因为编译+418 用例全过才没出事，纯文本/配置类文件没有这层保护。

### 2. 回测口径与结果（226 样本 / 19 个交易日 / 153 只去重）
口径：T 日 `t_market_stock` 涨停池中 `consecutive ≥ 2` 的票 → T+1 涨跌幅走腾讯 qfq 日 K `close(T+1)/close(T)−1`；T 日温度取 `t_daily_record.temperature`。无未来函数（T 日温度收盘后才算出）。

- **方差分解：日间（选时）11.0% / 日内（选股）89.0%**。温度是市场级同步变量，同日全部候选共享一个取值，**结构上不可能区分个股** → 温度只能当仓位旋钮，不能当选股因子；反过来个股评分也替代不了那 11%。
- 温度分档（**按天**统计，避免同日样本伪独立）：T<55 → 4 天 +2.16%/胜率61.0%；55–60 → 2 天 +1.59%/48.7%；60–70 → 6 天 +3.75%/68.0%；≥70 → 2 天 +5.84%/83.7%。方向单调但每档仅 2–6 天，**不构成可用规律**。
- 反例：温度最低的 09-04（42.5°）次日 **+7.19%、胜率 85.7%**，是全样本最好的一天 → 「低温就不做」是错的（冰点期赔率最高）。
- **温度没跑赢自己的原料**：温度与涨停家数相关 **+0.674**；而涨停家数单独用 vs 次日均涨 Pearson **+0.396**，温度只有 **+0.280**。
- 组合回测（每日等权买当日全部候选，次日收盘卖；信号检验，非可实现收益）：恒满仓 +56.59% → T≥60 才做日均从 +3.26% 升到 +4.24%，累计却掉到 +39.52%。**温度过滤提高单日质量、降低总收益**。
- 单因子 IC（n=226）：**封单/成交额 +0.308（最强）** ＞ 成交额 **−0.285（负向，越小越好）** ＞ 封单额 +0.222 ＞ 首次封板时间 +0.196 ＞ 情绪温度 +0.131 ＞ **连板数 +0.100（最弱）** ＞ 宽度分 b +0.001。高度分 h+溢价分 p 为 **−0.159（反向）**。
  → 直接推翻 `filter_min_amount = 1.0 亿`（方向做反了，已改 0.5 亿 + `MARK`）；连板数几乎无区分度，正是"单靠身位高度不足以过滤风险"的量化证据。

### 4. 环境再踩一次：`python -c` 里的反斜杠也会被吞

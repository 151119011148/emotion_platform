## 14 脚本的两条核心结论（对策略本身重要）
- **封单÷成交额是 T 日唯一能事前预警「T+1 买不进」的指标，且强单调**：
  `<15%`→8.4% 一字 ｜ `15~50%`→25.9% ｜ `50~150%`→28.6% ｜ `150~300%`→**52.9%** ｜ `≥300%`→**87.0%**。
  所以它在清单里的角色是**可执行性折价**，不是加分项——A 口径给它 +0.308 的「最强正向因子」纯属在挑买不到的票。
- **可执行子样本（gap≤3%，n=105）内 T 日因子排序力全部失效**：连板数 2/3/4/5 板非单调、成交额非单调、
  首封时间方向与 A 口径相反。→ 所以清单**按可执行性排序、等权、单票 5% 上限，不做因子加权**。
- 09-21 清单实测：21 候选 → 剔 2 只封单锁死（次日双双一字买不进）→ T+1 `gap≤3%` 成交 11 只 →
  占用资金 **+1.22%**、账户 +0.67%、胜率 63.6%；被 gap 挡下的 8 只里 5 只亏 3~15%（含 −14.76%）。
- **⚠️ 09-22 是 `gate=3%` 的第一次样本外检验，结果是负的**：L0 −0.81% / L1 −1.57% /
  **L2 −2.40%（胜率 23.1%）**，而被门槛挡下的 5 只平均 **+0.60%**，规律整体反转。
  → 坐实「+1.22% 是样本内结果」：`gate=3%` 只能当**执行纪律**（高开不追），不能当**择时规律**；
  要进默认配置需 ≥40 日样本 + 多阈值敏感性检验。**这条已写进页面 12.6 节原样呈现，不做粉饰。**

### 本期踩到的两个坑（做别的脚本也适用）

- 页面切片截图时若要只显示 `<section>` 内部的某一节：`#s12>*{display:none}` + `#s12-3{display:block}` +

### 调查：库里「题材」到底有没有通达信来源（结论：有，而且就是 t_stock_concept）
- **`t_stock_concept` 就是通达信题材板块成分**，不是它 Javadoc 里写的「东财 BKxxxx」：
  266 个 `concept_code` **100% 命中** `t_concept_board.board_code`，而后者是 V23/V33 从
  `infoharbor_block.dat` + `tdxbk.cfg` 导入的通达信板块字典（`index_code` 全是 880xxx）。
  行数 46149、去重 5411 只票，`updated_at` = V33 的安装时刻（09-22 09:12:09）→ 由迁移写入，非东财同步。
- `t_industry_stock`（5581 行）= 通达信**二级行业**（tdxhy.cfg 截 T+4）。
- **`t_market_stock.industry` 是东财行业且被截断成 4 个汉字**（「房地产开」「农产品加」「光学光电」），
  58 个行业名里只有 12 个能命中通达信行业字典 → 这就是原来「题材」列看着别扭的根因。
- **⚠️ 埋在 `ConceptIndexService.rebuild()`（`POST /api/review/concept-index/rebuild`）里的雷**：
  它 `mapper.delete(全部)` 后按**东财** ~504 个概念整盘重建 `t_stock_concept`
  → 一点就把通达信题材冲成东财题材。当前库里是通达信口径（没人点过），**已在该类 Javadoc 标注**，
  改不改行为交用户决策。
- **一只涨停票带 1~11 个通达信题材**（09-21 实测），所以「原样铺出来」不可行，必须排序 + 折叠。

### 实现

## 收尾：8080 掉线与我起的实例撞车

- 我用后台 `mvn spring-boot:run` 起的 8080（验收用）在 17:37:04 **被外部硬杀**
  ——`logs/emotion-server.log` 停在正服务请求的中间，**无 shutdown 序列、无异常堆栈**，
  后台任务报 `failed` 但 stderr 为空。判据：**日志戛然而止 + 无关闭日志 = 被 kill，不是崩溃**。
- 随后我发起的重启撞上 `PortInUseException: Port 8080 is already in use`——
  你在这几十秒内自己把后端拉起来了（新 PID 14696）。
- **教训**：检测到「端口没人听」不等于「可以随便起」——用户可能正在自己重启。
  起之前先看 `logs/emotion-server.log` 的 mtime 是否刚被写过，或直接问一句。
- 版本确认手段（值得复用）：新字段在**旧字节码的 VO 里根本不存在**，
  所以「响应里有没有这个键」本身就是版本判据，不必去猜进程命令行。
  实测 14696：`tdxThemes` 15/15、`nodeTags` 4 只、`nodeCount=0`（回滚生效），与验收完全一致。

## 一个新发现的真问题：`t_daily_bar` 并发 upsert 死锁

- 日志 `emotion-server.log` 里 **4 次** `日K落库失败 … Deadlock found when trying to get lock`，
  涉及 `sz000504 / sz000978 / sz002285 / sz301390`，全部发生在 pool-1-thread-N **同一毫秒**
  （多只票并发回源、各自 `upsertBatch`）→ 复合唯一键 `(symbol, trade_date)` 的**插入意向锁/GAP 锁互撞**。
- **影响可控**：`DailyBarService.store()` 已用 try-catch 兜住，失败只跳过「写缓存 + 留痕」，
  **回源那一手的数据已经返回给调用方了**，页面不受影响；代价是这几只票下次仍要回源。
  另：留痕与 bar 行在同一个 try 里，失败时**留痕也没写**，所以不会出现「留痕说有、其实没行」
  这种会掩盖停牌缺行的状态——这一点是设计对了。
- **同类先例已存在**：`SurveillanceService:182` 明确注释「上游拉取可以并发，**写库不行**：
  六路 INSERT … ON DUPLICATE KEY UPDATE 会在 uk_code_art 上互相…」并做了串行写。
  `DailyBarService` 少了这一层。修法二选一：①写库段加锁/单线程 executor 串行；
  ②捕获死锁后重试一次（`DeadlockLoserDataAccessException`）。**待定，未擅自改。**

## 候选池：加「一字断魂刀」执行预警 ＋ 删「最高板」身位标识

### 1. 一字断魂刀预警（用户指出「连板生态里有这个标识」）

- **判据只有一处**：`TiantiService.isDuanDao`（首封≤93030 且 0 炸板、连续两日、板数≥2、
  流通≤35亿、封单≥10亿 或 封成比≥3、换手<5%）。**没有复制第二份**——天梯页/连板生态
  是「按板数逐只判」，候选池是「给一批票问哪些中」，入口不同、判据同一个。
  新增 `TiantiService.duanDaoCodes(date, codes)` + 私有 `poolOn()`（**故意不走 `listPool`**：
  后者会跑 `industryClassify.apply`，而断魂刀判据一个字都不看行业）。
- **落点＝新瞬态字段 `CandidateStock.alertFlag`**（`@TableField(exist=false)`，取值 `ALERT_DUANDAO="DUANDAO"`），
  在 `WaveRiderController.tagAlerts(rows, date)` 里打，接在 `topicHeatService.tagTdxThemes` 旁边三处：
  `/run`、`/candidates`、`/export`。
- **为什么不能塞进 `risk_flag`**：`build()` 里 `if (c.getRiskFlag() != null) w = w * 0.5;` ——
  带 riskFlag 的仓位**折半**。「断魂刀」是**执行难度**（大概率排不到队），不是质地风险；
  而封单锁死恰恰是本策略最强的正向因子（封成比五档打板收益 +1.71→+7.56%）。
  把它当风险折半＝与「封单锁死不该剔除、反而靠前」的既定结论自相矛盾。**所以两个字段并存**：
  `alertFlag`＝买不买得到（不折仓、不改排序、不扣分），`riskFlag`＝要不要折算仓位。前端「警示」列两个标签并排。
- **导出**：md 加「警示」列（中文「一字断魂刀」），csv 加 `alert_flag`（**机器码 `DUANDAO`**，
  与同行 `risk_flag` 给码的做法一致）。
- **前端**：`风险` 列改名 `警示`，`alertText/alertTip` 两个函数（中文与悬浮解释在前端，
  判据不在前端）；悬浮文案要讲清「买不进 ≠ 不该选」。

### 3. 教训（重要，别再犯）

- **后台常驻的 `mvn spring-boot:run` 今天被外部杀掉两次**（一次是我起的 8090 验收实例、
  一次是 8091）。→ **验收改成「一条命令内自起自拆」**，别留长命后台进程：既验证得了，
  又不会和用户的 8080 抢 Quartz，也不会留下需要事后清理的端口。
- 脚本输出用 `python -u`：进程被信号杀时，缓冲区里的 print 会**全部丢失**（第一次验收
  零输出就是这么来的，看起来像「没跑」）。
- 断言别偷懒：这次 `'警示' in md.split('\n')[0]` 是**错的**——md 首行是标题不是表头；
  csv 里我给的是机器码、断言却找中文。**两个 FAIL 里有一个真问题（csv 该给机器码）**，
  另一个纯属断言写错。写断言时要按内容实际结构写，不要"想当然第一行"。

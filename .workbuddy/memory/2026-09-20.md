## 引入 Flyway + 单机定时任务平台（每天19点拉行情入库）
- 需求：每天 19:00 拉取当天数据落库，账号 gaofeng/123456；用户明确否决「脚本/计划任务」方案，要求用定时任务平台维护、SQL 用 Flyway 管，且要做单机版。
- Flyway：把 1978 行的 schema.sql 按原有时间线脚本切分（`Write` 一次性定义的行区间，搬完自校验非空行与原文件一致）成 `emotion-server/src/main/resources/db/migration/V1__…V24__*.sql`。去掉了原文开头 `CREATE DATABASE`/`USE`（Flyway 连的就是目标库）。
  - `application.yml`：baseline-on-migrate=true + baseline-version=24 → 空库从 V1 顺序建，存量库打基线跳过 V1–V24（那段有 DELETE+INSERT 种子收敛，重放会冲掉手工改的权重）；历史表 `t_flyway_history`；clean-disabled=true。
  - 依赖 flyway-core + flyway-mysql 同版本 8.5.13（对齐父 BOM 2.7.18 托管版本；Flyway 10 起 MySQL 支持已拆到独立模块）。
  - **拆分只是当前结构的切片**：原文件一直就地维护且没有 git 历史，中间版本的 CREATE 语句里已含后来补的列，不是当天历史原貌。
- 调度：spring-boot-starter-quartz + JDBC JobStore，QRTZ_* 与 `t_scheduler_job`/`t_scheduler_run` 建表在 V25（故 `spring.quartz.jdbc.initialize-schema=never`）。
  - 三层分工已在 README 第八节写清：t_scheduler_job（人维护排班）/ QRTZ_*（Quartz 状态，别手改）/ t_scheduler_run（执行留痕）。
  - 统一入口 `TaskDispatchJob`（配 `SpringBeanJobFactory` 才能注入），按 jobDataMap 里的 beanName 取 `ManagedTask` 执行。加任务 = 新 bean + 表里插一行。
  - 19:00 任务 `daily_market_pull` → `dailyMarketPullTask`：`MarketDataService.snapshot(今日,true)` 之外还要自己补 `MarketDailyStore.upsertSnapshot`（这一步原本挂在 MarketController 里，定时任务不走 HTTP）；非交易日返回 TaskResult.skip，不算失败。
  - 坑：不能配 `spring.quartz.startup-delay`，否则 ApplicationRunner 先于 Quartz 起来导致装载失败。
- 维护接口：`/api/scheduler/jobs`、`/reload`、`/jobs/{name}/cron`、`/jobs/{name}/enabled`、`/jobs/{name}/run`、`/runs`（走 Bearer token）。
- 验证：`mvn -DskipTests compile` 通过、`mvn test` 407 个用例全绿。**没做真库验证**——Flyway 首次迁移与 Quartz 首次装载需要起服务才能真验。
